EXECUTIVE SUMMARY
1.1 Project Overview
Petal is a specialized e-commerce platform designed to modernize the floral gifting industry.
Unlike generic marketplaces, Petal connects users with local artisan florists through a unique
"Mood-Based" search engine and a "Forget-Me-Not" automation system. The system
integrates a Spring Boot backend, a React web dashboard for florists, and an Android mobile
application for customers, ensuring seamless order fulfillment and recurring delivery
management.
1.2 Objectives
1. Develop a native Android application for customers to browse floral arrangements by
"Mood" (e.g., Romance, Apology).
2. Create a React-based web dashboard for florists to manage inventory and receive orders.
3. Implement a "Forget-Me-Not" automation system that triggers recurring reminders for
annual events (Anniversaries, Birthdays).
4. Deploy a secure Spring Boot REST API to orchestrate communication between buyers,
vendors, and the database.
5. Integrate location-based services to ensure delivery accuracy within local zones.
1.3 Scope
Included Features:
● User registration and authentication (Buyer & Florist roles).
● Mood-based product catalog with real-time inventory filtering.
● "Forget-Me-Not" calendar management for recurring events.
● Checkout process with specific Delivery Date/Time Slot selection.
● Florist Dashboard for order acceptance and status updates.
● "Proof of Delivery" photo upload functionality.

--- PAGE 5 ---
● PostgreSQL database with relational schema for Users, Orders, and Products.
Excluded Features:
● International shipping (Local/Hyperlocal delivery only).
● Wholesale/B2B bulk ordering system.
● Real credit card processing.
● Driver GPS tracking app.
● Automated SMS service
1.0 INTRODUCTION
1.1 Purpose
This document serves as the comprehensive design specification for the Petal application. It
provides detailed requirements, architectural decisions, API contracts, database design, and
implementation roadmap to guide development. It ensures that the emotional context of
gifting (Moods) and the logistical precision of delivery (Time Slots) are technically supported
across all system components.

2.2 Core User Journeys
Journey 1: The "Mood" Purchase
User visits web application
1. User visits the Petal app and selects the "I'm Sorry" mood tile.
2. System displays arrangements tagged with the selected mood.
3. User selects a bouquet and adds a personalized card message.
4. User selects a Delivery Date and Time Slot.
5. User completes checkout using Mock Payment; Order status becomes "PENDING".
Journey 2: The "Forget-Me-Not" Reminder
1. User navigates to "Important Dates" in their Profile.
2. User adds "Wife's Birthday" (Feb 14) and toggles "Remind Me".
3. System saves the date with is_recurring = true.
4. Three days before the event, the User receives an email/app notification.
Journey 3: Administrator Product Management
1. Florist logs into the Florist Web Portal.
2. Views new order in the "Pending" column of the Kanban board.
3. Clicks "Accept" → Order moves to "Arranging".
4. Once delivered, Florist clicks "Complete" → Status updates to "DELIVERED" on the Buyer's
dashboard.

2.5 Acceptance Criteria
AC-1: Florist Storefront Setup and Visibility
● Given I am a newly registered user logged in as a Florist
● When I upload my store logo and fill out my bio and address in the Store Settings page
● Then the system should save my profile to the database
● And Buyers browsing the mobile app should instantly see my logo and bio attached to
my listed products.
AC-2: Buyer Mood Search Accuracy
Ø Given I am a Buyer on the home screen
Ø When I tap the "Sympathy" mood tile
Ø Then the system should display only products tagged with "sympathy" in the
database
Ø And I should not see "Romance" or "Celebration" products in the results list.
AC-3: Delivery Scheduling Constraints
Ø Given I am a Buyer navigating the checkout flow
Ø When I open the Delivery Date calendar to schedule my order
Ø Then all past dates must be disabled and unselectable

--- PAGE 10 ---
Ø And if a Florist has reached their daily maximum capacity, that specific date must be
greyed out.
AC-4: Two-Sided Order Status Sync
Ø Given a Buyer has placed an order successfully
Ø When the Florist moves the order to the "Delivered" column on their Web Dashboard
Ø Then the order status in the database should immediately update to "DELIVERED"
Ø And the Buyer should see this updated status reflected in their mobile app order
history.
AC-5: Forget-Me-Not Trigger Functionality
Ø Given a Buyer has saved an "Anniversary" event set for February 14th
Ø When the system's internal clock reaches February 11th (exactly 3 days prior)
Ø Then the backend scheduler must trigger an automated reminder notification to the
Buyer
Ø And no duplicate notifications should be sent for that specific year.
3.0 NON-FUNCTIONAL REQUIREMENTS
3.1 Performance Requirements
● API Response Time: GET /products must respond in ≤ 200ms to ensure smooth
scrolling.
● Concurrency: System must support 300% traffic load during peak holidays (Valentine's
Day, Mother's Day).
● Inventory Locking: Cart items must be reserved for 10 minutes to prevent
double-booking.
● Database queries must complete within 500ms under normal load.
3.2 Security Requirements
● HTTPS for all client-server communications.
● JWT token authentication with role-based access control.
● Data Encryption: Recipient address and card message data must be encrypted at rest
(AES-256).

--- PAGE 11 ---
● PCI-DSS Compliance: No raw credit card data stored; tokenization via mock payment
layer.
● Privacy: Driver-visible recipient phone numbers must be masked.
● Rate Limiting: 100 requests/minute per IP address.
● Role-Based Access: Only ROLE_FLORIST users can access the inventory dashboard.
3.3 Compatibility Requirements
● Mobile: Android 7.0 (Nougat / API Level 24) and higher.
● Web: Chrome, Firefox, Safari, Edge (latest 2 versions).
● Screen Sizes: Mobile (360px+), Tablet (768px+), Desktop (1024px+).
● Operating Systems: Windows 10+, macOS 10.15+, Linux Ubuntu 20.04+.
3.4 Usability Requirements
● One-Handed Navigation: Primary action buttons (Buy, Next, Confirm) placed in the
bottom 30% of the mobile screen.
● Visual Clarity: Product images must be high-resolution but WebP optimized (<200KB
per image).
● Error Recovery: Clear, actionable messages for failed states (e.g., "This florist is fully
booked for this date. Please try tomorrow.").
● Complete first purchase within 5 minutes for new users.
● Touch targets minimum 44×44px on mobile.
● WCAG 2.1 Level AA compliance for web interface.

6.0 DATABASE DESIGN
6.1 Entity Relationship Diagram
Detailed Relationships:
● One-to-One: User ↔ Florist (A florist account maps to exactly one user record)
● One-to-Many: Florist → Products (A florist lists multiple products)
● One-to-Many: User → Orders (A buyer places multiple orders)
● One-to-Many: User → Saved_Dates (A buyer saves multiple important dates)
● One-to-Many: User → Address_Book (A buyer saves multiple recipient addresses)

--- PAGE 28 ---
● Many-to-One: Orders → Products (An order references one product)
● One-to-Many: Products → Product_Mood_Tags (A product has multiple mood tags)
Key Tables:
1. users – User accounts, authentication, and role assignment
2. florists – Florist storefront details linked to a user account
3. products – Product catalog managed by florists
4. product_mood_tags – Mood tag associations for each product
5. orders – Customer orders with delivery and status details
6. saved_dates – Buyer's Forget-Me-Not important dates
7. address_book – Buyer's saved recipient addresses
Table Structure Summary:
● users: user_id, first_name, last_name, email, password_hash, phone, role, created_at
● florists: florist_id, user_id, store_name, bio, logo_url, street, city, zip_code,
max_daily_capacity
● products: product_id, florist_id, name, description, price, image_url, in_stock,
created_at
● product_mood_tags: tag_id, product_id, mood
● orders: order_id, buyer_id, product_id, florist_id, recipient_name, recipient_address
(encrypted), card_message (encrypted), delivery_date, time_slot, status,
proof_image_url, created_at
● saved_dates: date_id, user_id, label, event_date, is_recurring, notified_year
● address_book: address_id, user_id, label, recipient_name, street, city, zip_code, phone
